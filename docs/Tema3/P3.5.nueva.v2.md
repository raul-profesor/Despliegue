# Práctica 3.4: Despliegue de una aplicación Flask

## 1. Objetivos

Al finalizar la práctica, seremos capaces de:

- Explicar la arquitectura de tres capas de una aplicación web Python: servidor web (Nginx), servidor de aplicaciones WSGI (Gunicorn) y framework de aplicación (Flask).
- Explicar qué es WSGI, qué es Flask como *microframework* y en qué consiste el patrón MVC.
- Gestionar las dependencias de un proyecto Python con `uv` y crear entornos virtuales reproducibles.
- Desplegar una aplicación Flask mínima y, posteriormente, una aplicación real completa desde un repositorio de GitHub.
- Desplegar **dos aplicaciones simultáneas** en el mismo servidor, cada una con su propio servicio, socket y virtual host.
- Crear una unidad de servicio de `systemd` robusta, con reinicio automático, recarga sin downtime y directivas de hardening.
- Configurar Nginx como proxy inverso hacia Gunicorn utilizando un socket Unix, **resolviendo correctamente los permisos** del socket.
- Diagnosticar los errores más habituales del proceso de despliegue.

## 3. Conocimientos previos

### 3.1. Las tres piezas de una aplicación web

Una aplicación web en Python se compone de **tres piezas**:

| Pieza | Qué hace | Ejemplos |
|---|---|---|
| **Servidor web** | Recibe las peticiones HTTP de los navegadores y las reparte | Nginx, Apache |
| **Servidor de aplicaciones WSGI** | Traduce las peticiones HTTP a llamadas WSGI y ejecuta varios procesos de la aplicación | Gunicorn, uWSGI, Waitress |
| **Framework web** | El código de la aplicación: rutas, plantillas, datos | Flask, Django, FastAPI |

**WSGI** (Web Server Gateway Interface) es un estándar que define cómo se comunican el servidor web y la aplicación Python. Gracias a él, la aplicación no necesita saber si delante hay Nginx o Apache, y tú te centras en programar en vez de en gestionar la comunicación.

```mermaid
graph LR
    C[Cliente<br/>navegador] -->|HTTP :80| N[Nginx<br/>proxy inverso]
    N -->|socket Unix| G[Gunicorn<br/>master + 4 workers]
    G -->|WSGI| A[Flask<br/>wsgi:app]
    A --> T[Plantillas Jinja2<br/>y ficheros estáticos]
```

El recorrido de una petición es corto:

1. El navegador abre una conexión contra el **puerto 80** y envía una petición HTTP.
2. **Nginx** recibe la petición y, como no corresponde a un fichero estático, la envía al *proxy inverso*.
3. **Gunicorn** tiene un proceso *master* que acepta la conexión y la reparte entre sus procesos *worker*.
4. El *worker* ejecuta la función de la ruta Flask, renderiza la plantilla y devuelve la respuesta, que recorre el camino inverso hasta el cliente.

!!! info "El modelo de Gunicorn: prefork"
    Gunicorn lanza varios procesos *worker*, cada uno con su propia copia de la aplicación Python. El *master* los vigila y **reemplaza automáticamente** al que muere. Es el mismo modelo que usa PHP-FPM con Apache.

### 3.2. Flask y el patrón MVC

**Flask** es un «micro» framework en Python para crear aplicaciones web bajo el patrón **MVC**. La palabra «micro» no significa que el proyecto sea pequeño: significa que trae lo esencial y que el resto se añade con *extensiones* (plugins).

| Capa | Responsabilidad | En Flask |
|---|---|---|
| **Modelo** | Los datos de la aplicación | Objetos Python, ORM (SQLAlchemy), ficheros |
| **Vista** | La presentación en HTML | Plantillas Jinja2 en `templates/` |
| **Controlador** | La gestión de las peticiones | Funciones decoradas con `@app.route()` |

### 3.3. Entornos virtuales y `uv`

Un **entorno virtual** es una copia aislada del intérprete de Python con sus propios paquetes. Lo que instalas en un entorno no se ve desde ningún otro, así que cada aplicación puede tener sus propias dependencias sin interferir.

`pip` es el gestor de paquetes clásico de Python. `uv` es su equivalente moderno (escrito en Rust, de Astral, los creadores de `ruff`): sustituye a `pip` + `venv` + `pipenv` con una sola herramienta y es entre 10 y 100 veces más rápido.

| Función | Clásico | Con `uv` |
|---|---|---|
| Instalar paquetes | `pip install` | `uv pip install` |
| Crear el entorno | `python3 -m venv .venv` | `uv venv` |
| Instalar un `requirements.txt` | `pip install -r requirements.txt` | `uv pip install -r requirements.txt` |
| Ver lo instalado | `pip list` | `uv pip list` |
| Fijar versiones exactas | `pip freeze` | `uv pip freeze` |
| Instalar Python si no lo tienes | No | `uv python install 3.12` |

!!! tip "Sin `uv` también se puede"
    El equivalente exacto con herramientas estándar es `python3 -m venv .venv && source .venv/bin/activate && pip install -r requirements.txt`.

    Todo lo demás de la práctica (ruta del ejecutable, unidad de `systemd`, configuración de Nginx) es **exactamente igual**, porque lo importante es la ruta al binario `gunicorn` dentro del entorno virtual.

## 4. Arquitectura que vamos a montar

En esta práctica trabajaremos con **dos** aplicaciones:

| | **PoC** (`mi_app`) | **Real** (`atletismo`) |
|---|---|---|
| Origen | Ficheros escritos a mano | Repositorio Git clonado |
| Contenido | Una sola ruta que devuelve un `<h1>` | Records mundiales de atletismo con mapa interactivo |
| Ficheros | `application.py` + `wsgi.py` | Paquete `app/` con datos, API y vistas separados |
| Origen de los datos | En el código | `data/records.json` |
| Dependencia externa | Ninguna | API de elevación de Open-Meteo |
| Sonda de salud | No | Sí (`/health`) |

### 4.1. Aplicación PoC

Consta de dos ficheros. `application.py` contiene la aplicación Flask, y `wsgi.py` sólo la importa y la expone como objeto WSGI, que es lo que Gunicorn espera:

```python
# application.py
from flask import Flask

app = Flask(__name__)


@app.route("/")
def index():
    return "<h1>Mi aplicacion Flask</h1><p>Desplegada con Nginx + Gunicorn</p>"
```

```python
# wsgi.py
from application import app

# Gunicorn espera encontrar un objeto WSGI llamado 'app' en este módulo
__all__ = ["app"]
```

!!! info "¿Por qué un `wsgi.py` aparte?"
    Separa la **aplicación** (lo que despliega el desarrollador) del **punto de entrada** que consume el servidor. Además, Gunicorn necesita una **ruta de importación** con dos componentes: `archivo:objeto`. En este caso, `wsgi:app`.

### 4.2. Aplicación real: records de atletismo

Publicada en [https://github.com/raul-profesor/atletismo-records](https://github.com/raul-profesor/atletismo-records).

Muestra los **records mundiales vigentes de medio fondo y fondo de atletismo**, indicando **dónde y cuándo** se consequieron, mediante un mapa interactivo (Leaflet + OpenStreetMap) en el que el tamaño de cada marcador es proporcional a la altitud del terreno.

Incluye:

- Un **mapa interactivo** con un marcador por recinto.
- Una **tabla filtrable** por categoría, sexo, modalidad y texto libre.
- Una **API JSON**: `/api/records`, `/api/recintos`, `/api/altitud`.
- Una **sonda de salud** en `/health`, pensada para engancharla a `systemd`.

**¿Por qué esta aplicación?** Porque los records de atletismo dependen del terreno. El maratón de Londres (16 m sobre el nivel del mar) y el de Chicago (181 m) no son comparables entre sí. La altitud del recinto es una **variable de primer orden**, y por eso un mapa que la muestre es informativo y no un adorno.

La estructura del proyecto separa los datos, el acceso a servicios externos, las rutas y las plantillas:

```text
atletismo/
├── app/
│   ├── __init__.py          # Rutas Flask
│   ├── datos.py             # Carga y filtrado de los datos
│   ├── elevacion.py         # Consulta a la API de Open-Meteo
│   ├── templates/index.html
│   └── static/{css,js}/
├── data/records.json        # 19 records en 12 recintos
├── requirements.txt
└── wsgi.py                  # Punto de entrada para Gunicorn
```

!!! note "Los datos"
    `data/records.json` contiene 19 records en 12 recintos, con coordenadas y una altitud **estimada**. La altitud **exacta** se consulta en tiempo de ejecución a la [API de elevación de Open-Meteo](https://open-meteo.com/en/docs/elevation-api).

    La aplicación incorpora **degradación elegante**: si esa API no responde, registra un aviso en el log y sigue funcionando con la altitud estimada.

## 5. Preparación del servidor

Todos los comandos de esta sección deben ejecutarse desde una terminal con permisos de administración.

### Paso 1: Actualizar el sistema e instalar el software

```bash
sudo apt update
sudo apt upgrade -y
sudo apt install -y python3 python3-venv python3-pip git nginx
```

Comprobamos las versiones:

```bash
cat /etc/os-release
python3 --version
git --version
nginx -v
```

### Paso 2: Crear un usuario de servicio dedicado

!!! danger "Nunca ejecutes la aplicación como `root`"
    Tampoco como tu usuario personal. El enunciado original usaba `chown -R $USER:www-data`: la aplicación se ejecutaba con los permisos de tu usuario de trabajo, así que una vulnerabilidad en tu aplicación daba un shell en el servidor con **tus** privilegios, incluida tu clave SSH y tu acceso a `sudo`.

    Lo correcto es un **usuario de sistema**, sin shell y sin permisos reales.

```bash
sudo useradd \
    --system \
    --home /opt/flask \
    --shell /usr/sbin/nologin \
    --user-group \
    flask

id flask
```

!!! note "Por qué `/opt/flask` y no `/var/www`"
    `/var/www` es la raíz de documentos por defecto de Apache. `/opt` es la convención para software de terceros instalado por el administrador. Además, **Nginx no necesita leer nada de nuestra aplicación**: sólo mantiene una conexión con Gunicorn.

Ahora hacemos que **Nginx** (`www-data`) forme parte del grupo `flask`. **Este paso es imprescindible**: sin él, Nginx no podrá conectarse al socket y todo el despliegue fallará con `502 Bad Gateway`.

```bash
sudo usermod -aG flask www-data
id www-data
```

Deberías ver `www-data` con el grupo `flask` entre los suyos:

```text
uid=33(www-data) gid=33(www-data) groups=33(www-data),<GID de flask>
```

!!! danger "Reinicia Nginx: los grupos se leen al arrancar el proceso"
    `usermod` **no** afecta a los procesos ya en marcha. El proceso master de Nginx sigue con sus grupos antiguos y, por tanto, sin acceso al socket.

    ```bash
    sudo systemctl restart nginx
    ```

    Un `reload` **no** sirve: recarga la configuración pero conserva los grupos del proceso ya iniciado.

!!! info "Por qué `www-data` tiene que estar en el grupo `flask`"
    Para conectarse a un socket Unix hace falta permiso de **escritura** (`w`) sobre él. El kernel concede ese acceso al propietario, a los miembros del **grupo** del socket, o a "otros".

    El socket lo crea Gunicorn con el **GID primario** del proceso, es decir `flask:flask`. Como `www-data` es miembro del grupo `flask`, el kernel le aplica los bits de grupo del socket (`rwx`) y puede conectarse.

    !!! danger "El error sutil: `SupplementaryGroups=www-data` NO sirve"
        Añadir `SupplementaryGroups=www-data` al servicio **no** funciona, porque ese grupo no es el del socket: los bits de grupo se aplican al grupo *primario* del fichero. El resultado sería un `502 Bad Gateway` inexplicable.

        Y si además pones `Group=www-data`, el socket se creará `flask:www-data` en lugar de `flask:flask`, que es justo lo que queremos evitar.

### Paso 3: Crear la estructura de directorios

```bash
sudo mkdir -p /opt/flask/apps/mi_app /opt/flask/apps/atletismo
sudo chown -R flask:flask /opt/flask
ls -la /opt/flask/apps/
```

```text
drwxr-xr-x 2 flask flask 4096 ... atletismo
drwxr-xr-x 2 flask flask 4096 ... mi_app
```

!!! danger "Este paso no es opcional"
    Los directorios **deben existir y ser de `flask`** antes de crear el entorno virtual. Si el directorio es de `root`, el `uv venv` fallará:

    ```text
    error: Failed to create virtual environment
      cause: failed to create directory `.venv`: Permission denied (os error 13)
    ```

    El error engaña: dice «Permission denied» sobre `.venv`, pero el `.venv` **no existe todavía**. Lo que falla es crear el directorio dentro de `mi_app`, que pertenece a `root`. La solución es **arreglar el propietario del directorio padre**:

    ```bash
    sudo chown -R flask:flask /opt/flask
    ```

La estructura final será:

```text
/opt/flask/apps/
├── mi_app/          <- Aplicación PoC
│   ├── .venv/       <- Entorno virtual
│   ├── application.py
│   ├── wsgi.py
│   └── requirements.txt
└── atletismo/       <- Aplicación real
    ├── .venv/
    ├── app/
    ├── data/
    ├── wsgi.py
    └── requirements.txt
```

### Paso 4: Instalar `uv` y crear el entorno virtual

!!! danger "Instala `uv` en `/usr/local/bin`"
    Si lo instalas en tu `home` (`~/.local/bin`), **no funciona con `sudo -u flask`** por dos motivos:

    1. `sudo` sustituye tu `PATH` por su `secure_path`, que no incluye `~/.local/bin` → `sudo: uv: command not found`.
    2. Tu `home` suele tener permisos `700`, así que el usuario `flask` no puede **atravesarlo** para llegar al binario → `sudo: unable to execute .../uv: Permission denied`.

    En `/usr/local/bin` no hay ninguno de los dos problemas.

```bash
curl -LsSf https://astral.sh/uv/install.sh | sudo env UV_INSTALL_DIR=/usr/local/bin sh
/usr/local/bin/uv --version
```

!!! tip "`uv` como paquete del sistema"
    En Debian 13 (Trixie) y Ubuntu 25.04 o superiores está disponible como paquete nativo: `sudo apt install uv`. En versiones anteriores, el script instala una versión bastante más reciente, que es la opción preferible.

Creamos el entorno virtual e instalamos **Flask y Gunicorn**:

```bash
cd /opt/flask/apps/mi_app
sudo -u flask uv venv --python 3.12
sudo -u flask uv pip install flask gunicorn
```

!!! info "¿Por qué `sudo -u flask`?"
    Para que el entorno virtual pertenezca al usuario del servicio y no a tu usuario personal.

    !!! danger "Lo que NO hay que hacer"
        No uses `sudo uv ...` sin `-u flask`. El entorno virtual quedaría propiedad de `root` y el servicio `systemd` no podría usarlo.

!!! note "`flask` es el servidor de desarrollo, `gunicorn` el de producción"
    El paquete `flask` trae la biblioteca y el ejecutable `flask` (servidor de desarrollo). El paquete `gunicorn` trae el ejecutable `gunicorn` (servidor de producción) que usaremos detrás de Nginx.

Comprobamos dónde han quedado los ejecutables:

```bash
cd /opt/flask/apps/mi_app
sudo -u flask uv pip list
ls -la .venv/bin/
```

!!! info "Los ejecutables viven en `.venv/bin/`"
    Aparecen `flask`, `gunicorn` y `python`. **Esta es la ruta que usaremos en la unidad de `systemd`**: `/opt/flask/apps/mi_app/.venv/bin/gunicorn`. Nunca usaremos simplemente `gunicorn`, porque el `PATH` del servicio es distinto del de tu shell.

Guardamos las dependencias para poder recrear el entorno:

```bash
cd /opt/flask/apps/mi_app
sudo -u flask sh -c 'uv pip freeze > requirements.txt'
```

!!! danger "Cuidado con la redirección `>`"
    Escribir `sudo -u flask uv pip freeze > requirements.txt` **no funciona**: el símbolo `>` lo interpreta **tu shell**, no `sudo`, así que el fichero se intenta abrir con **tu usuario**. Como el `requirements.txt` pertenece a `flask`, obtenemos:

    ```text
    -bash: requirements.txt: Permission denied
    ```

    La solución es meter la redirección **dentro** del `sudo`, usando `sh -c` (como arriba). Así el fichero se crea con el usuario `flask` y con sus permisos.

### Paso 5: Crear los ficheros de la aplicación

```bash
cd /opt/flask/apps/mi_app
sudo -u flask touch application.py wsgi.py
```

Editamos `application.py` y `wsgi.py` con el contenido del [apartado 4.1](#41-aplicacion-poc).

## 6. Probar la aplicación en local

Antes de montar nada, comprobamos que la aplicación funciona. Veremos **dos** formas de ejecutarla:

### Servidor de desarrollo de Flask

```bash
cd /opt/flask/apps/mi_app
sudo -u flask .venv/bin/flask --app wsgi run --host 0.0.0.0 --port 5000
```

Accedemos desde el navegador a `http://IP-DEL-SERVIDOR:5000`.

!!! warning "Este servidor NO es apto para producción"
    - Usa un único proceso y un único hilo: no atiende peticiones en paralelo.
    - Avisa explícitamente en su banner de que no es estable.
    - No reinicia los *workers* si uno falla.
    - No se integra con `systemd` ni con la rotación de logs.

    Sirve para desarrollo. Lo que usaremos en producción es Gunicorn.

Detenemos el servidor con `CTRL+C`.

### Gunicorn en un puerto TCP

```bash
cd /opt/flask/apps/mi_app
sudo -u flask .venv/bin/gunicorn --workers 4 --bind 0.0.0.0:5000 wsgi:app
```

| Opción | Significado |
|---|---|
| `--workers 4` | Número de procesos *worker*. La regla habitual es `2 × nproc + 1` (ver `nproc`) |
| `--bind 0.0.0.0:5000` | Escucha en todas las interfaces en el puerto 5000 |
| `wsgi:app` | El archivo `wsgi.py` y el objeto `app` que hay dentro |

!!! info "La sintaxis `módulo:objeto`"
    Gunicorn importa el módulo `wsgi` y busca en él un atributo llamado `app`. Como `wsgi.py` hace `from application import app`, ese atributo es el objeto Flask, que es un *callable* WSGI válido.

La salida debe parecerse a esto:

```text
[2026-11-08 18:30:12 +0100] [12345] [INFO] Starting gunicorn 26.2.0
[2026-11-08 18:30:12 +0100] [12345] [INFO] Listening at: http://0.0.0.0:5000 (12345)
[2026-11-08 18:30:12 +0100] [12345] [INFO] Using worker: sync
[2026-11-08 18:30:12 +0100] [12346] [INFO] Booting worker with pid: 12346
[2026-11-08 18:30:12 +0100] [12347] [INFO] Booting worker with pid: 12347
[2026-11-08 18:30:12 +0100] [12348] [INFO] Booting worker with pid: 12348
[2026-11-08 18:30:12 +0100] [12349] [INFO] Booting worker with pid: 12349
```

Detenemos Gunicorn con `CTRL+C`.

## 7. Convertir Gunicorn en un servicio de `systemd`

En producción queremos que la aplicación arranque sola al encender el servidor, se reinicie sola si se cuelga y se pueda consultar con las herramientas del sistema. Para eso creamos una **unidad de servicio**.

### Paso 6: Decidir dónde vive el socket Unix

Nginx y Gunicorn están en **la misma máquina**, así que no tiene sentido abrir un puerto TCP entre ellos: usamos un **socket Unix**, que es un fichero especial del sistema de ficheros.

La primera decisión es **dónde** va ese socket. La opción production es usar la directiva `RuntimeDirectory=` de `systemd`, que crea el directorio al arrancar el servicio, le asigna como propietario al usuario del servicio y lo borra al pararlo.

!!! danger "Un `RuntimeDirectory` por servicio, nunca compartido"
    `RuntimeDirectory=` para servicios de sistema se resuelve siempre bajo `/run/`, y el directorio **se elimina por completo cuando el servicio se para**.

    Si las dos aplicaciones de esta práctica declararan `RuntimeDirectory=flask`, al parar un servicio **se borraría el socket del otro**, que se quedaría con un `502 Bad Gateway` sin explicación. Además, al arrancar, `systemd` hace un `chown -R` de todo lo que hay bajo ese directorio al usuario del servicio, así que el último en arrancar reasignaría los sockets del otro.

    Por eso cada servicio declara **su propio** directorio:

    | Servicio | `RuntimeDirectory` | Socket resultante |
    |---|---|---|
    | `flask-app.service` | `flask-app` | `/run/flask-app/mi_app.sock` |
    | `flask-atletismo.service` | `flask-atletismo` | `/run/flask-atletismo/atletismo.sock` |

### Paso 7: Escribir la unidad de servicio

```bash
sudo nano /etc/systemd/system/flask-app.service
```

```ini
[Unit]
Description=Mi aplicacion Flask servida por Gunicorn
After=network.target

[Service]
Type=simple
User=flask
Group=flask

WorkingDirectory=/opt/flask/apps/mi_app

# El PATH empieza por el venv, para que 'gunicorn' sea el del entorno virtual
Environment="PATH=/opt/flask/apps/mi_app/.venv/bin"

# Variables de entorno de la aplicacion (el '-' evita que falle si no existe)
EnvironmentFile=-/opt/flask/apps/mi_app/.env

ExecStart=/opt/flask/apps/mi_app/.venv/bin/gunicorn \
    --workers 4 \
    --bind unix:/run/flask-app/mi_app.sock \
    --umask 0007 \
    --access-logfile - \
    --error-logfile - \
    --timeout 30 \
    --graceful-timeout 30 \
    wsgi:app

# Recarga sin downtime: HUP hace que Gunicorn reinicie los workers
ExecReload=/bin/kill -s HUP $MAINPID

Restart=always
RestartSec=5
KillSignal=SIGQUIT
TimeoutStopSec=30

# Directorio de runtime: /run/flask-app, con el usuario del servicio
RuntimeDirectory=flask-app

# 0755: Nginx debe poder RECORRER el directorio para llegar al socket
RuntimeDirectoryMode=0755

# Gunicorn 27 intenta crear un socket de control para sus comandos de
# administracion. Con ProtectSystem=strict no puede, y el journal muestra:
#   [ERROR] Control server error: [Errno 30] Read-only file system
# No es fatal (el servicio sigue funcionando), pero se evita con:
ControlSocket=none

# Hardening
NoNewPrivileges=true
PrivateTmp=true
ProtectSystem=strict
ProtectHome=true
ProtectKernelTunables=true
ProtectKernelModules=true
ProtectControlGroups=true
RestrictSUIDSGID=true
RestrictNamespaces=true
LockPersonality=true

[Install]
WantedBy=multi-user.target
```

!!! info "Qué hace cada directiva"
    | Directiva | Función |
    |---|---|
    | `After=network.target` | Arranca **después** de que la red esté lista |
    | `User` / `Group` | Identidad con la que se ejecuta la aplicación: **nunca root** |
    | `WorkingDirectory` | Directorio desde el que se ejecuta Gunicorn (donde están `templates/` y `static/`) |
    | `Environment="PATH=..."` | Pone el venv **al principio** del `PATH` |
    | `EnvironmentFile=-...` | Carga las variables del `.env`. El prefijo `-` indica que el fichero es opcional |
    | `ExecStart` | El comando de arranque, con la **ruta absoluta** al ejecutable |
    | `--bind unix:...` | **Crea el socket Unix** que Nginx consumirá |
    | `--umask 0007` | Permisos del socket: `srwxrwx---`. Los miembros del grupo `flask` (Nginx) pueden conectarse |
    | `--access-logfile -` | Los logs de acceso van a `stdout`, que systemd captura en el journal |
    | `--timeout 30` | Si un worker tarda más de 30 s, se le mata y se reinicia |
    | `ExecReload` + `HUP` | Recarga los workers sin tumbar el servicio |
    | `Restart=always` + `RestartSec=5` | Si el proceso muere, systemd lo reinicia tras 5 s |
    | `KillSignal=SIGQUIT` | Al parar, Gunicorn termina los workers de forma ordenada |
    | `RuntimeDirectory` | systemd crea `/run/flask-app` con el usuario correcto y lo limpia al parar |
    | `RuntimeDirectoryMode=0755` | Permisos del directorio: **todos pueden recorrerlo** |
    | `ControlSocket=none` | Evita el error `Control server error: Read-only file system` del journal |

!!! warning "El bloque de hardening no es decorativo"
    `ProtectSystem=strict` hace que todo el sistema de ficheros sea de **sólo lectura** para el servicio. `ProtectHome=true` impide que el servicio lea tu `/home`. `PrivateTmp=true` le da su propio `/tmp` aislado. `NoNewPrivileges=true` impide ganar privilegios mediante `setuid`.

    Todo esto limita mucho el daño si alguien consigue ejecutar código dentro de la aplicación.

!!! note "El `.env` de la aplicación"
    ```bash
    sudo -u flask touch /opt/flask/apps/mi_app/.env
    sudo -u flask nano /opt/flask/apps/mi_app/.env
    ```

    Contenido típico:

    ```text
    FLASK_APP=wsgi:app
    FLASK_ENV=production
    SECRET_KEY=una-clave-larga-y-aleatoria
    ```

    !!! danger "Nunca subas el `.env` al repositorio"
        Contiene secretos. Debe estar en el `.gitignore` y tener permisos restrictivos: `sudo chmod 640 /opt/flask/apps/mi_app/.env`

```bash
sudo systemctl start flask-app
sudo systemctl status flask-app
```

### Paso 9: El socket y sus permisos

Este es el punto más importante de la práctica. **Compruébalo antes de configurar Nginx.**

Para que Nginx (usuario `www-data`) pueda hablar con Gunicorn a través del socket hacen falta **tres cosas**:

| Elemento | Permiso | Por qué |
|---|---|---|
| `www-data` en el grupo `flask` | `usermod -aG flask www-data` | Para que el kernel le aplique los bits de grupo del socket |
| `/run/flask-app/` (directorio) | `0755` | Nginx debe poder **recorrer** el directorio para llegar al socket |
| `/run/flask-app/mi_app.sock` (socket) | `srwxrwx---` `flask:flask` | Los miembros del grupo `flask` (Nginx) pueden conectarse |

!!! danger "El error clásico: `502 Bad Gateway` por permisos del socket"
    Hay **dos** motivos distintos que producen el mismo `502`, y conviene distinguirlos:

    **1. El directorio no tiene permiso de recorrido.** Si `/run/flask-app` está en modo `0750` y es de `flask:flask`, el usuario `www-data` **no puede atravesar** el directorio padre. El socket puede existir y ser `srwxrwx---`, pero para abrirlo hay que recorrer `/run/flask-app`. Nginx recibe `EACCES` y responde `502 Bad Gateway`.

    → Solución: `RuntimeDirectoryMode=0755`.

    **2. `www-data` no pertenece al grupo del socket.** El socket lo crea Gunicorn con el **GID primario** del proceso, o sea `flask:flask`. Si `www-data` no es miembro del grupo `flask`, el kernel le aplica los bits de "otros" (sin `w`) y la conexión falla.

    → Solución: `sudo usermod -aG flask www-data` (Paso 2).

!!! danger "Si `curl` dice `Failed to connect to localhost port 80`"
    Este mensaje es **muy engañoso**: aunque uses `--unix-socket`, `curl` muestra el puerto del URL (`http://localhost/` → 80) en el error. **No significa que esté ignorando el socket.**

    Con `curl -v` se ve lo que ocurre de verdad:

    ```text
    * Trying /run/flask-app/mi_app.sock:0...
    * Connected to localhost (/run/flask-app/mi_app.sock) port 80
    ```

    Es decir, `curl` **sí** intenta el socket; lo que falla es el `connect()`. Y como el socket lo crea Gunicorn con el **GID primario** del proceso, el `connect()` sólo prospera si `www-data` es miembro del grupo `flask`:

    ```bash
    sudo usermod -aG flask www-data
    sudo systemctl restart nginx
    ```

    Comprueba el permiso de escritura directamente:

    ```bash
    sudo -u www-data test -w /run/flask-app/mi_app.sock && echo "TIENE w" || echo "NO tiene w"
    ```

    !!! tip "Y si el socket no existe en absoluto"
        Si `/run/flask-app/` está **vacío**, el servicio no llegó a arrancar. La causa habitual es una **opción inexistente** en el `ExecStart`: Gunicorn **no tiene `--chmod`** (la opción real es `--umask`), y un argumento desconocido aborta el arranque:

        ```text
        gunicorn: error: unrecognized arguments: --chmod wsgi:app
        ```

        Mira el error real en el journal y corrige la unidad:

        ```bash
        sudo journalctl -u flask-app -n 30 --no-pager
        ```

Comprobamos los permisos reales:

```bash
ls -la /run/flask-app/
```

```text
srwxrwx--- 1 flask flask 0 ... /run/flask-app/mi_app.sock
```

!!! tip "Por qué `--umask 0007`"
    Gunicorn crea el socket con permisos `666` enmascarados por el `umask`:

    | `--umask` | Socket resultante | ¿Nginx conecta? |
    |---|---|---|
    | `0027` | `srwxr-x---` | No: al grupo le falta el `w` que exige `connect()` |
    | **`0007`** | **`srwxrwx---`** | **Sí** ✓ |

    Con `0007` el socket queda `srwxrwx---`: el propietario (`flask`) y los miembros de su grupo (Nginx) pueden conectarse, y los demás no.

    !!! note "El grupo del socket"
        El socket se crea con el **GID primario** del proceso, que es `flask`. Por eso sale `flask flask` y no `flask www-data`: el fichero pertenece al grupo del servicio, no al de Nginx.

Y probamos que **Nginx** (no sólo el usuario `flask`) puede conectar al socket:

```bash
sudo -u www-data curl --unix-socket /run/flask-app/mi_app.sock http://localhost/
```

```text
<h1>Mi aplicacion Flask</h1><p>Desplegada con Nginx + Gunicorn</p>
```

!!! tip "Este paso es la clave de la práctica"
    En el enunciado original, la configuración de Nginx apuntaba a un socket `unix:` que **nadie creaba nunca**, y los alumnos se encontraban con un `502 Bad Gateway` sin ninguna pista de por qué. Con esta comprobación, el error aparece en el minuto 20 y no en el minuto 45.

## 8. Nginx como proxy inverso

### Paso 10: Configurar el virtual host

```bash
sudo nano /etc/nginx/sites-available/flask-app
```

```nginx
server {
    listen 80;
    listen [::]:80;

    server_name flask-app flask-app;

    server_tokens off;
    client_max_body_size 10m;

    access_log /var/log/nginx/flask-app.access.log;
    error_log  /var/log/nginx/flask-app.error.log;

    # Los ficheros estaticos los sirve Nginx directamente, sin pasar por Gunicorn
    location /static/ {
        alias /opt/flask/apps/mi_app/static/;
        expires 30d;
        access_log off;
    }

    location / {
        # OJO: NO incluyas 'include proxy_params;' aqui.
        # Ya pone 'proxy_set_header Host $proxy_host;', y si anades
        # tambien 'proxy_set_header Host $host;' Nginx envia DOS cabeceras
        # Host y Gunicorn 27 las rechaza con un 400 Bad Request.

        # Proxy inverso hacia el socket Unix de Gunicorn
        proxy_pass http://unix:/run/flask-app/mi_app.sock;

        proxy_http_version 1.1;
        proxy_set_header Host              $host;
        proxy_set_header X-Real-IP         $remote_addr;
        proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_redirect off;

        proxy_connect_timeout 5s;
        proxy_read_timeout    60s;
    }
}
```

!!! info "Comentarios sobre la configuración"
    - **`server_name`**: los nombres de dominio que responderá este virtual host. Los resolveremos con `/etc/hosts` en el [Paso 12](#paso-12-resolver-el-nombre-y-verificar).
    - **`server_tokens off`**: no revela la versión de Nginx en las cabeceras de respuesta.
    - **`location /static/`**: Nginx sirve directamente los ficheros estáticos, sin molestar a Gunicorn. Las CSS y las imágenes son las peticiones más frecuentes y no requieren ejecutar Python.

!!! danger "`Host` duplicado: `400 Bad Request` con Gunicorn 27"
    En Debian y Ubuntu, el fichero `/etc/nginx/proxy_params` ya contiene:

    ```nginx
    proxy_set_header Host $proxy_host;
    ```

    Si además escribes tú `proxy_set_header Host $host;`, Nginx envía **dos** cabeceras `Host`. Gunicorn 27 aplica la RFC 9110 §5.3, según la cual `Host` es un campo **singleton**: una segunda ocurrencia hace la petición ambigua y la rechaza.

    El síntoma en el journal de Gunicorn es:

    ```text
    [WARNING] Invalid request from ip=: Invalid HTTP Header: 'HOST'
     - - [11/Nov/2026:12:56:32 +0000] "GET / HTTP/1.1" 400 0 "-" "-"
    ```

    Y el navegador muestra un error, aunque la aplicación esté perfecta.

    **Solución**: quitar `include proxy_params;` y dejar las cabeceras explícitas, como en la configuración de arriba. Si prefieres mantener el `include`, entonces **no** escribas la línea `proxy_set_header Host $host;`.

!!! danger "El detalle de la barra final en `proxy_pass`"
    Si escribimos `proxy_pass http://unix:/run/flask-app/mi_app.sock;` **sin barra final**, Nginx reenvía la URI original sin modificarla. Si le añadimos una barra final (`.../socket/`), Nginx **elimina el prefijo** de la URI y las rutas de la aplicación dejan de funcionar.

!!! tip "Variante con TCP en lugar de socket Unix"
    Si prefieres la versión con puerto (más fácil de depurar con `curl http://127.0.0.1:8000`), el `ExecStart` sería `--bind 127.0.0.1:8000` y en Nginx `proxy_pass http://127.0.0.1:8000;`

    !!! warning "El puerto 80 es exclusivo de Nginx"
        Gunicorn **no** debe escuchar en el 80: lo hace Nginx, que es el servidor web. Si le asignas el 80 a Gunicorn, el servicio no arrancará con `Address already in use`.

        Con la variante TCP, el socket ya no es un fichero, así que **no hay problema de permisos**: es mucho más simple de depurar, a cambio de abrir un puerto (aunque sólo en `127.0.0.1`).

### Paso 11: Habilitar el sitio y recargar Nginx

```bash

ls -l /etc/nginx/sites-enabled/ | grep flask-app
```

!!! note "`sites-available` frente a `sites-enabled`"
    Es una convención de Debian y Ubuntu: `sites-available` contiene todas las configuraciones posibles; `sites-enabled` contiene los enlaces simbólicos a las que Nginx realmente dará servicio. Así se activa o desactiva un sitio con un simple `ln -s` o `rm`.

Comprobamos que la configuración no tiene errores y recargamos:


!!! danger "Si hiciste `usermod -aG flask www-data`, reinicia Nginx (no recargues)"
    Un `reload` recarga la configuración pero **conserva los grupos** del proceso ya iniciado, así que Nginx seguiría sin acceso al socket y devolvería `502`.


!!! info "`reload` frente a `restart`"
    `reload` pide a Nginx que **recargue la configuración sin tumbar las conexiones existentes**. Es la forma correcta de aplicar cambios.

### Paso 14: Crear el servicio systemd

Esta aplicación necesita **su propio servicio**, **su propio socket** y **su propio virtual host**. Copia la unidad del Paso 7 y cambia **cinco líneas**:

```bash
sudo cp /etc/systemd/system/flask-app.service /etc/systemd/system/flask-atletismo.service
sudo nano /etc/systemd/system/flask-atletismo.service
```

| Línea | Valor en `flask-atletismo.service` |
|---|---|
| `Description` | `Records de atletismo (Flask + Gunicorn)` |
| `WorkingDirectory` | `/opt/flask/apps/atletismo` |
| `Environment="PATH=..."` | `/opt/flask/apps/atletismo/.venv/bin` |
| `ExecStart` | `.venv/bin/gunicorn` + `--bind unix:/run/flask-atletismo/atletismo.sock` |
| `RuntimeDirectory` | `flask-atletismo` |

La sección `[Service]` queda así:

```ini
[Unit]
Description=Records de atletismo (Flask + Gunicorn)
After=network.target

[Service]
Type=simple
User=flask
Group=flask
WorkingDirectory=/opt/flask/apps/atletismo
Environment="PATH=/opt/flask/apps/atletismo/.venv/bin"
EnvironmentFile=-/opt/flask/apps/atletismo/.env
ExecStart=/opt/flask/apps/atletismo/.venv/bin/gunicorn \
    --workers 4 \
    --bind unix:/run/flask-atletismo/atletismo.sock \
    --umask 0007 \
    --access-logfile - \
    --error-logfile - \
    --timeout 30 \
    --graceful-timeout 30 \
    wsgi:app
ExecReload=/bin/kill -s HUP $MAINPID
Restart=always
RestartSec=5
KillSignal=SIGQUIT
TimeoutStopSec=30
RuntimeDirectory=flask-atletismo
RuntimeDirectoryMode=0755
ControlSocket=none
NoNewPrivileges=true
PrivateTmp=true
ProtectSystem=strict
ProtectHome=true
ProtectKernelTunables=true
ProtectKernelModules=true
ProtectControlGroups=true
RestrictSUIDSGID=true
RestrictNamespaces=true
LockPersonality=true

[Install]
WantedBy=multi-user.target
```

!!! danger "`RuntimeDirectory=flask-atletismo`, no `flask`"
    Si lo dejáramos en `RuntimeDirectory=flask`, los dos servicios compartirían el mismo directorio. Al parar uno, systemd lo borraría **entero**, llevándose por delante el socket del otro. Y al arrancar, el `chown -R` reasignaría la propiedad de los sockets del otro servicio.

```bash
sudo systemctl status flask-atletismo
```


Y probamos cada uno por separado, sin pasar por Nginx:


## 12. Diagnóstico rápido

### Entorno y dependencias

| Problema | Causa probable | Solución |
|---|---|---|
| `sudo: uv: command not found` | `sudo` sustituye el `PATH` por su `secure_path` y `uv` está en `~/.local/bin` | Instala `uv` en `/usr/local/bin` (Paso 4) |
| `sudo: unable to execute .../uv: Permission denied` | El usuario `flask` no puede recorrer tu `home`, que tiene permisos `700` | Instala `uv` en `/usr/local/bin` (Paso 4) |
| `failed to create directory '.venv': Permission denied` | El directorio del proyecto es de `root`, así que `flask` no puede escribir dentro | `sudo chown -R flask:flask /opt/flask` (Paso 3) |
| **`-bash: requirements.txt: Permission denied`** | La redirección `>` la hace **tu shell**, no `sudo`, así que intenta escribir el fichero con tu usuario | Mete la redirección dentro: `sudo -u flask sh -c 'uv pip freeze > requirements.txt'` (Paso 4) |
| `No virtual environment found` | No hay `.venv` en el directorio, o el `uv venv` anterior falló | `uv venv --python 3.12` y arregla los permisos del directorio |
| `ModuleNotFoundError: No module named 'flask'` | Se ejecutó el Python del sistema, no el del venv | Usa `.venv/bin/python` o `.venv/bin/flask` |
| `error: externally-managed-environment` (pip) | Se intentó instalar en el Python del sistema | Instala siempre dentro del venv, o usa `uv pip` |

### El socket y sus permisos

| Problema | Causa probable | Solución |
|---|---|---|
| **`502 Bad Gateway` y el socket sí existe** | `www-data` no puede **recorrer** el directorio del socket (`RuntimeDirectoryMode=0750`) | `RuntimeDirectoryMode=0755` |
| **`502 Bad Gateway` y el socket es `flask:flask`** | `www-data` no pertenece al grupo `flask`, así que el kernel le aplica los bits de "otros" (sin `w`) | `sudo usermod -aG flask www-data` (Paso 2) y reinicia Nginx |
| **`502 Bad Gateway` y el socket no existe** | Gunicorn no está corriendo, o el `RuntimeDirectory` se borró | `sudo systemctl status flask-app` y `ls -la /run/flask-app/` |
| **`curl` dice `Failed to connect to localhost port 80`** | El mensaje es engañoso: `curl` **sí** usa el socket (compruébalo con `curl -v`), pero el `connect()` falla | Comprueba el permiso: `sudo -u www-data test -w /run/flask-app/mi_app.sock`. Si falla, `sudo usermod -aG flask www-data` + `sudo systemctl restart nginx` |
| **`/run/flask-app/` vacío y `curl` dice `port 80`** | El servicio **no arrancó**: Gunicorn falló y no creó el socket | `sudo journalctl -u flask-app -n 30 --no-pager` para ver el error. Causa típica: una opción **inexistente** en el `ExecStart` (Gunicorn no tiene `--chmod`) |
| `Control server error: [Errno 30] Read-only file system` en el journal | Gunicorn 27 no puede crear su socket de control porque `ProtectSystem=strict` deja el sistema de ficheros en sólo lectura | No es fatal. Añade `ControlSocket=none` a la unidad |
| `Permission denied` al crear el socket | El directorio de runtime no pertenece al usuario del servicio | `RuntimeDirectory=` en la unidad (Paso 7) |
| **El socket sale `flask:www-data`** | La unidad tiene `Group=www-data` (o `SupplementaryGroups` con ese grupo), así que el GID efectivo del proceso no es `flask` | Pon `Group=flask` en la unidad y usa `sudo usermod -aG flask www-data` (Paso 2) |
| **El socket de una app desaparece al parar la otra** | Ambas comparten `RuntimeDirectory` y systemd lo borra al parar | Un `RuntimeDirectory` **distinto** por servicio (Paso 6) |
| El socket cambia de propietario al reiniciar la otra app | El `chown -R` recursivo de `systemd` sobre un directorio compartido | Un `RuntimeDirectory` **distinto** por servicio (Paso 6) |
| `Connection refused` al usar el socket | Gunicorn no está corriendo o el socket no existe | `systemctl status flask-app` y `ls -la /run/flask-app/` |

### Gunicorn

| Problema | Causa probable | Solución |
|---|---|---|
| `ModuleNotFoundError: No module named 'wsgi'` | Se usó `wsgi:app` en un repo que sólo tiene `app.py` | Usa `app:app` |
| `ModuleNotFoundError: No module named 'app'` | Se usó `app:app` en un proyecto que sólo tiene `wsgi.py` | Usa `wsgi:app` |
| `Address already in use` | El puerto 5000 ya está ocupado | `ss -lntp \| grep 5000` |
| `WORKER TIMEOUT` en los logs | Un worker tarda más de `--timeout` segundos | Aumenta `--timeout` o revisa las consultas lentas a la base de datos |

### Nginx

| Problema | Causa probable | Solución |
|---|---|---|
| `502 Bad Gateway` | Gunicorn no corre, o la ruta del socket no coincide con el `--bind` | Compara `proxy_pass` con el `--bind unix:` de la unidad |
| `404 Not Found` | `proxy_pass` con barra final | Elimina la barra final: `proxy_pass http://unix:/run/flask-app/mi_app.sock;` |
| **`400 Bad Request` y el journal dice `Invalid HTTP Header: 'HOST'`** | Nginx envía **dos** cabeceras `Host`: una del `include proxy_params;` y otra del `proxy_set_header Host $host;`. Gunicorn 27 rechaza el `Host` duplicado (RFC 9110 §5.3) | Quita `include proxy_params;` y deja las cabeceras explícitas (Paso 10) |
| `403 Forbidden` | Permisos de los ficheros estáticos | `sudo chown -R flask:flask /opt/flask/apps/atletismo/app/static` |
| No se ven los estilos | `location /static/` con `alias` mal escrito | La ruta del `alias` debe terminar en `/` y coincidir con el directorio real |

### DNS y resolución de nombres

| Problema | Causa probable | Solución |
|---|---|---|
| `ERR_NAME_NOT_RESOLVED` | El `/etc/hosts` de la máquina local no tiene la línea | Edita el fichero de tu máquina **anfitriona**, no el del servidor |
| `ERR_CONNECTION_REFUSED` en el navegador | El puerto 80 está bloqueado por el cortafuegos o el grupo de seguridad | `sudo ufw allow 80/tcp` y revisa el grupo de seguridad de la VM |
| `ping` funciona pero el navegador no | Se editó el `/etc/hosts` equivocado | Recuerda: el del portátil, no el del servidor |
